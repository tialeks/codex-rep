# Tables for Agent

## Обязательная последовательность работы

При подготовке макетов выполнять этапы строго по порядку. Пропуск редакторской проверки запрещён, даже если текст получен из таблицы, формы, старого макета или уже присутствует в инстансе.

1. **Условия.** [Tables for Agent](SKILL.md) нормализует условия, сохраняя ID оффера, методы оплаты, числовые значения и различия между наградой и действием задания. Для ручного ввода использовать те же смысловые поля. Публикация нормализованной таблицы в Tracker выполняется, когда это входит в задачу.
2. **Русская редактура.** [Редактура СУВ](../suv-texts-1/SKILL.md) проверяет весь RU-текст по редакторскому промту. Для задания отдельно проверить состояния до и после получения.
3. **Английская версия.** Если запрошена EN, читать правила перевода и глоссарий редакторского скилла, переводить проверенный RU и сверять смысл, числа, термины и длину. Неразрешённый конфликт глоссария и длины показать пользователю до финализации затронутого EN-текста. Для RU-only этот этап неприменим.
4. **Макет.** [SUV Layouts Creator](../figma-automation/SUV-layouts-creator/SKILL.md) собирает ячейки и шторки из проверенных текстов с библиотечными компонентами.
5. **Проверка результата.** Сверить тексты макета с результатом редактуры и исходными условиями. Любое изменение формулировки в процессе сборки повторно провести через редактуру и соответствующий перевод.

Для каждого оффера передавать дальше его ID, методы, исходные числа и условия, RU-строки по блокам, EN-строки при необходимости и статусы выполненных проверок. Статус проверки ставить только после её выполнения. Не объявлять весь комплект завершённым при непроверенном обязательном этапе.
Формулировки, подписи, инструкции и legal определяет редакторский модуль. Иерархию, компоненты, токены, размеры, иконки и переносы — генератор СУВ. Исторические тексты макетов в references не отменяют согласованную редактуру.


## Сценарий работы

1. Принять ссылку на исходную таблицу и определить тикет назначения из запроса или текущего контекста. Если тикет назначения не определён, прочитать и подготовить таблицу, затем запросить ссылку или ключ тикета для публикации.
2. Открыть исходную таблицу по присланной ссылке в режиме чтения. Определить вкладку, строку заголовков и диапазон с офферами. Учитывать объединённые ячейки, явные общие условия и примечания, которые применяются к строкам. Если источник указан в тикете, использовать штатный доступ Tracker и читать приложенный лист по прямой ссылке. Для скриншотов использовать только реально полученные вложения. При обрезанных заголовках сверять с источником. Если доступ закрыт, запросить нужный диапазон или файл.
3. Привести офферы к схеме ниже и сверить готовый результат с источником. Если обязательные данные конфликтуют или отсутствуют, подготовить доступную часть и уточнить спорные значения до публикации. Однозначные необязательные пропуски не считаются препятствием.
4. Опубликовать нормализованную таблицу **в указанном тикете Яндекс Трекера**. По умолчанию добавить комментарий. Обновлять описание, только если сотрудник попросил разместить результат в описании. Google-таблица в этом сценарии служит источником. Результат оформляется непосредственно в тикете.
5. Перечитать комментарий или описание штатным инструментом Tracker и сверить опубликованный текст, число строк и колонки. Вернуть ссылку на тикет или комментарий. При ошибке публикации сохранить готовую таблицу и сообщить, что запись в тикете не подтверждена.

[СУВ — условия для макетов](https://docs.google.com/spreadsheets/d/121lHz13G3hIfwEiqi2IrfFg50bMGOeqbXeldb3wMFRE/edit?gid=1018018200#gid=1018018200) — пример формата. Схема ниже полностью описывает колонки и доступна без доступа к примеру.

## Колонки рабочего шаблона

| Колонка | Что записывать |
| --- | --- |
| ID оффера | Стабильный смысловой ID, общий для строк одной будущей шторки. Не переносить номера строк источника, в том числе в ID. |
| Категория | Название для макета. Если в условиях написано капсом, сохранить капс. Для опций — «Опция „Амедиатека“ в Плюсе», «Опция „Старт“ в Плюсе». |
| Вид категории | «Обычная категория», «Опция Плюса» или «Задание с наградой». PEGAS, ADAMAS, Такси и комбо-офферы — обычные категории, если в условиях нет отдельного задания. |
| Условие получения категории | Обязательно для задания. Записать конкретное действие, открывающее награду. |
| № метода | «Метод 1», «Метод 2» и далее. Задаёт порядок блоков одного оффера. |
| Способ оплаты | Оплата самой выгоды. Условия оплаты выполнения задания указывать в условии задания, если они отличаются. |
| Тип выгоды, Значение, Ед. | Кешбэк баллами Плюса или скидка. Число и единица — раздельно. |
| На что действует, Где действует | Объект и канал покупки раздельно. Для скидки уточнить доставку, покупку в Сплит или иной объект по источнику. |
| Порог, ₽ | Минимальная сумма покупки для выгоды. |
| Лимит, баллы / Период лимита | Сумма и период отдельно. |
| Доп. лимит, баллы / Период доп. лимита | Второй лимит и его период, если они есть. |
| Отложка, дней | Число дней из явной отложки или формулировки «баллы начисляются через N дней». Сохранять рабочие дни или другое событие отсчёта, если указано явно. |
| Исключения | Ограничения действия оффера с их исходным смыслом. |
| Наличие кнопки | Обычный текст «Да» по умолчанию. При отсутствии кнопки продакт пишет «Нет». Выпадающий список не нужен. |

Дополнительные данные передавать, если они есть в источнике: срок категории (для подписки или бейджа), сервис выполнения, отдельные подписи и назначения CTA до/после получения, описание и материалы. Пустая необязательная ячейка означает отсутствие параметра; ноль не подставлять. «Уточнить» использовать для реального противоречия или нехватки обязательных данных. Если период основного или дополнительного лимита не указан, записывать **«Нет»** в колонке периода и сохранять сумму лимита. Не считать такой лимит месячным. Явные периоды «За один заказ», «За транзакцию», «За месяц» и «За весь период» не смешивать.

## Группировка и оплата

- Одна строка задаёт один способ оплаты и связанные с ним условия. Разные способы или выгоды в одном оффере идут отдельными строками с общим ID. Это позволяет сохранить, например, кешбэк по карте и скидку в Сплит, включая отдельную скидку на доставку.
- Если в источнике перечислены несколько процентов и метод, объект, канал, тарифы, пороги, лимиты, отложка, исключения и описание совпадают, выбрать **один из явно указанных** процентов для образца. Например, 5% из ряда 3/5/7/10/15/20% для одинаковых условий Такси. Если хоть одно условие различается, сохранять отдельный вариант. Конфликт ставки между полями источника уточнять.
- «Через Яндекс Пэй», «по кнопке Пэй» и их смысловые варианты нормализовать как **«Любая карта через Яндекс Пэй»**. Сочетание **paybox + любая карта**, включая «Paybox — любая карта или QR», также записывать в таблице как **«Любая карта через Яндекс Пэй»**. Самостоятельная «Любая карта» без этих условий остаётся отдельным способом. Учитывать явные исключения и сноски об оплате из источника. Отдельные CP‑QR/MP‑QR сценарии выделять только при их явно описанных условиях.
- Явный текст CTA передавать дословно. Если кнопка есть и текст отсутствует, передать генератору отсутствие подписи для применения его дефолта. Не терять разные CTA двух состояний задания.
- Пример из таблицы: у Музторга «отложка 21» означает 21 день после покупки. У Рив Гош срок 21 день, исключения — СБП, сертификат, оплата картой курьеру, самовывоз, покупка подарочных карт. Иллюстративные 14 дней и карты рассрочки из другого макета к нему не относятся.

## Распознавание заданий

Проверять заголовки, отдельные колонки, пояснения и сами условия. Формулировки «задание», «задание с наградой», «категория с наградой», «выполнить задание, чтобы открыть/активировать категорию» и смысловые производные обозначают эту механику. Искомый смысл — **условие действия, за которое открывается категория**, а не точное совпадение одной строки.

Упоминание награды/вознаграждения само по себе в описании обычного кешбэка не доказывает наличие задания. Не путать обычный порог «кешбэк при покупке от X» с отдельным действием для активации награды. При неоднозначности спросить, а не достраивать механику.

Для каждого задания выделить получаемую категорию и действие. Сервис действия, вид, цель и метод оплаты сохранять, когда они применимы. Они могут относиться к разным сервисам. Явный выбранный вид имеет приоритет над общим оформлением обычных категорий; если он противоречит ясным условиям таблицы, уточнить конфликт до сборки. Отсутствие отдельной колонки вида не является основанием игнорировать явно описанное задание.

Источники ссылок и группы нескольких скриншотов остаются независимыми. Внутри одного материала могут быть разные виды категорий: классифицировать строки по смыслу и не размечать весь лист по одному случайному слову.


АП/АФ для Плюса — «Задание с наградой». Условие: «Подключить автопополнение или автофондирование Карты Пэй». Награда: Яндекс Плюс, подписка на месяц, 50% по Карте Пэй, лимит 449 баллов, период «Нет». Сервис выполнения — Пэй, сервис награды — Плюс. Для этого условия не придумывать сумму, число транзакций или прогресс. Опции Плюса остаются видом «Опция Плюса» и могут давать кешбэк или скидку.

## Распознавание источника по таблицам и скриншотам

Определять источник **сразу по смыслу**, включая производные, падежи, регистр, опечатки и близкие формулировки. Искать в явном поле источника/механики, заголовке таблицы или блока, формулировке получения категории и связанных примечаниях. Для сопоставления нормализовать пробелы, регистр, ё/е и невидимые символы, но исходные пользовательские условия не переписывать из-за этой нормализации.

- **Крутилка:** «крутилка», «из крутилки», «за крутилку», «попалась в крутилке», «попалось в крутилке», «выпала в крутилке», «барабан», «вращение барабана» и смысловые производные механики → `wheel`.
- **За уровень:** «за уровень», «от уровня», «награда за уровень», «золотой уровень», «получена за достижение уровня» и смысловые производные уровня как источника выгоды → `level`.
- **Баллдёж:** «Баллдёж», «Баллдеж», «из Баллдежа», «за Баллдёж», `baldezh`, `balldezh` и производные → `balldezh`.
- **Селектор:** «селектор», «выбрана в селекторе», «выбранная категория», «категория месяца» и формулировки самостоятельного выбора категории → `selector`.

Не требовать точного совпадения с dropdown. Это семантическая классификация источника, а не переименование самой категории. Обычные слова «выпала» или «уровень» вне контекста получения выгоды недостаточны. Если данные однозначны, не переспрашивать только из-за другой формулировки. При реальном противоречии нескольких источников уточнить привязку. Явное поле источника в строке имеет приоритет над общим источником блока только при отсутствии противоречия; конфликт не скрывать.

Для неизвестного конкретного уровня можно определить класс `level`, но нельзя молча назвать серебряный или иной уровень золотым. В этом случае сохранить конкретику и запросить/найти подтверждённые заголовок и вариант иконки. Подтверждённый текущий визуальный пример — золотой.

Если источник не указан и контекст не противоречит селектору, использовать Селектор. Явно указанный в материалах источник сохранять.


## Проверка перед публикацией

- Сверить состав офферов, их смысловые ID, порядок методов и принадлежность к источнику выгоды. В исходной таблице могут быть отдельные примечания для части строк. Не распространять их на остальные автоматически.
- Сверить числа, единицы, охват, каналы, условия оплаты, оба лимита с периодами, отложку, исключения и кнопку. У задания отдельно проверить действие для получения и условия награды. Провести эту проверку по переданным данным, без подстановки цифр из примеров.
- Если источник прямо требует обработать определённые вкладки, строки или визуально отмеченные группы, соблюдать этот охват. Номера строк использовать только внутри проверки. В тексте тикета не добавлять колонку или ID на их основе.
- В выходной строке указывать «Нет» для отсутствующего необязательного условия. Число 0 передавать только тогда, когда оно задано и имеет смысл. Для «Наличие кнопки» действуют отдельные значения по умолчанию.
- Дополнительные сведения без отдельной колонки (например, подписи кнопок до и после получения) сохранять после таблицы с указанием ID оффера и при необходимости номера метода. При нескольких независимых источниках выгоды можно разделить блоки заголовками источников.

## Формат комментария в Tracker

Использовать таблицу в синтаксисе YFM Tracker. Первая строка — `#|`, каждая строка таблицы обрамлена `||`, ячейки разделены `|`, последняя строка — `|#`. Сохранять точные 19 заголовков и их порядок из схемы. Проверить, что в каждой строке по 19 ячеек. Случайные переводы строк внутри ячейки заменить пробелами, если они не несут смысла. Если в значениях встречаются вертикальные черты, экранировать их в YFM как `\\|`, чтобы они не стали разделителями. В начале комментария можно указать ссылку на источник. [Пример для Tracker](references/tracker-example.md).

Если запрошены макеты, передать нормализованные условия сначала в редактуру (RU, затем EN при необходимости), затем в SUV Layouts Creator по обязательной последовательности выше.
