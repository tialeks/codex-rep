# Code Connect, Аркадия, Storybook и замена на компонент ДС

Цель — дать дизайнеру проверяемый ответ: связан ли UI с кодом, существует ли
готовая реализация и можно ли заменить ручной/устаревший блок компонентом ДС.
Проверка только читает источники. Не создавай mappings, stories, коммиты,
компоненты и публикации в рамках ревью. Инструкции инструментов по созданию
Code Connect не означают поручения создавать его при проверке наличия.

## Область и источники

Проверь каждое используемое семейство и каждого кандидата на замену из
library-usage.md. Общие результаты по одному компоненту можно переиспользовать,
но варианты и overrides конкретных блоков сверяй отдельно.

Определи целевые платформу, пакет/библиотеку, репозиторий, ревизию или релиз и
Storybook по задаче, KB, существующим mappings и документации ДС. Не подставляй
привычный репозиторий, адрес стенда или React-компонент для иной платформы.
Для Аркадии используй доступный поиск/чтение исходников и применимые правила
доступа; это не поручение выполнять VCS-операции. Для Storybook подходят живой
стенд, индекс stories и исходники stories, но различай эти виды доказательств.

Если адрес или нужный пакет неизвестен, сначала ищи в доступном контексте.
Если не удалось установить, задай один конкретный вопрос о недостающем источнике,
продолжая независимую часть ревью. Не проси настроить доступ к источнику, который
уже доступен. Не обходи ограничения доступа и не выдавай память о прошлой версии
за текущее состояние.

## Три независимые проверки

### Code Connect

- Читай существующие mappings для master компонента/набора и значимых вложений.
  Для detached-фрейма проверяй mapping найденного эталона ДС: у самого frame
  его закономерно может не быть.
- Запиши Figma identity/key, имя кодового компонента и source/import из mapping.
  Проверь, что ссылка ведёт на нужный компонент, платформу и актуальную версию;
  сравни значимые props/variants. Mapping может вести на wrapper или пример,
  а не публичный компонент библиотеки.
- Пустой ответ означает «mapping не найден в проверенном объёме», а отказ доступа
  — «не проверено». Ни один из этих результатов не означает, что кода нет.

### Аркадия: реализация и доступность

- Прочитай исходник кандидата и публичный export нужного пакета. Подтверди путь,
  имя/import, платформу, версию/ref проверки и статус: доступен, deprecated,
  внутренний/экспериментальный либо ещё не включён в нужный релиз.
- Сопоставь API с UI: контент, варианты, размеры, иконки/слоты, состояния,
  interactions, адаптивность, themes/tokens и необходимые данные — только то,
  что применимо к проверяемому блоку. Сходство имён или наличие файла недостаточны.
- Код в trunk не доказывает, что компонент доступен в версии продукта. Если
  используемая версия неизвестна, явно оставь это ограничением оценки замены.
  Недоступный исходник не заменяй сгенерированным MCP-сниппетом как доказательством.

### Storybook: демонстрация нужного сценария

- Найди конкретный story ID/URL и проверь релевантные states/args/controls,
  доступные свойства и ограничения. Сравни с вариантом макета; при визуальном
  сравнении просмотри рендер. Один default-story не доказывает покрытие всех состояний.
- Исходник stories подтверждает наличие примера в репозитории, но не его публикацию
  на стенде. Живой Storybook может отставать от Аркадии: отмечай версии и конфликты,
  не выбирай автоматически тот источник, который выглядит новее.
- Отсутствие story не доказывает отсутствие реализации. Наличие story также не
  доказывает публичный export или доступность компонента в версии продукта.

Для каждой поверхности используй один статус: **подтверждено**, **не найдено в
проверенном скоупе**, **не проверено** или **конфликт источников**. Указывай ссылки,
пути и проверенный объём поиска; не утверждай глобальное отсутствие по одному запросу.

## Оценка замены

Дай два отдельных вывода: **замена в Figma** и **использование в коде**.
Готовый instance в макете не доказывает доступность реализации, а готовый код
не восстанавливает библиотечную связь у detached-фрейма.

| Оценка | Основание |
| --- | --- |
| Без доработки ДС | Нужный вариант и сценарий покрыты штатными props/slots, размеры/layout/темы совместимы; для кода подтверждены public export и доступность в целевой версии. Для Figma проверено сохранение контента и нужных свойств при замене. |
| Нужна адаптация использования | Готовый компонент подходит, но требуются перестройка контейнера, перенос overrides/данных или mapping значений на штатные props. Назови конкретные изменения; не называй это заменой без проблем. |
| Нужна доработка ДС | Существенного состояния/свойства/варианта нет, компонент deprecated без подходящего преемника либо подтверждена несовместимость. Перечисли разрывы, которые требуется обсудить с владельцем ДС. |
| Недостаточно данных | Не проверены эталон, API, доступность версии или значимое поведение. Назови недостающий факт и вопрос, а не обещай лёгкую замену. |

«Без доработки ДС» не означает нулевую трудоёмкость миграции, автоматический swap
без проверки или оценку разработки в часах. Если совместимость обоснована чтением
контрактов, но реальная замена не выполнялась, называй её оценкой по контракту.

Если под заменой подразумевается изменение самого общего компонента ДС, отдельно
обозначь возможное влияние на его потребителей, необходимость миграции и проверки
обратной совместимости. Не делай вывод «без проблем» без данных о потребителях;
полный аудит библиотеки не входит в ревью фичи.

## Вопросы и уведомления

В отчёте явно сообщи для каждого проблемного семейства: чего нет/что не проверено,
какова оценка замены, какой ответ нужен и кто может его дать по роли. Например:
владелец ДС — допустимость расширения API; разработчик продукта — версия пакета;
дизайнер/продакт — обязательность отличающегося поведения.

Разделяй вопрос, блокирующий рекомендацию замены, и вопрос, блокирующий основной
продуктовый путь. Не превращай всё в блокер и не создавай квоту вопросов. Вопросы
возвращай в чат/отчёт; не отправляй коллегам и не публикуй их без поручения.
