# Целостность макета: компоненты, variables и styles

Проверяй использование системы внутри фичи. Цель — выявить потерю связей, неверные
компоненты и оформление, которое перестанет следовать библиотеке или темам.
Не исправляй и не публикуй библиотеку в ходе ревью.

## Источник правил и полный обход

Определи используемую библиотеку по задаче, правилам проекта, исходным masters,
доступным Code Connect mappings и явно принятому выбору дизайнера. Список включённых
библиотек сам по себе не означает, что каждая из них разрешена для фичи.
Отсутствие опубликованного Code Connect само по себе не ошибка макета.

Пройди дерево каждого целевого экрана целиком: instances, их вложенные элементы,
обычные frames/groups, текст, векторы и fills/strokes/effects. Скрытые части внутри
целевых экранов также инвентаризируй, но отличай их от активного интерфейса.
Для огромного дерева читай порциями и своди результаты. Не объявляй полный обход
после обработки только верхнего уровня, первой страницы ответа или выборки.
Соседние архивы и другие версии вне выбранной секции не входят в обход.

Собери node ID, тип, путь, видимость и применимые свойства: main component identity
и overrides для instances, bindings для поддерживающих их свойств. Не требуй
component identity у обычного текста/вектора. Для variables/styles читай идентификаторы,
источники и нужные modes; не запрашивай всю библиотеку без необходимости.
Если инструмент не умеет читать какое-то свойство, укажи «не проверено».

## Компоненты и detaches

Проверяй две разные выборки. Успешная проверка оставшихся instances ничего не
говорит о блоках, которые уже стали обычными frames/groups.

### 1. Существующие instances

У каждого instance проверь main component (key/источник), предназначение и variant.
У составных блоков проверь вложенные instances, заменённые иконки, слоты и контролы.
Связанный внешний контейнер не доказывает целостность его содержимого.
Поддерживаемые text overrides, instance swaps, booleans и slots нормальны; сам
факт override не означает detach. Недоступный remote master — ограничение доступа,
а не доказанный разрыв связи.

### 2. Обычные frames/groups в роли UI-компонентов

Этот проход обязателен даже при отсутствии сведений об истории detach.

1. По всему целевому дереву выдели блоки, выполняющие самостоятельную UI-роль:
   карточки лимита или выгоды, алерты, кнопки, строки списка, поля и другие
   повторяемые элементы. Проверь также обычные блоки внутри instances. Названия,
   повторяющаяся структура и иконка frame в Layers — сигналы для отбора кандидатов,
   а не самостоятельное доказательство detach.
2. Для каждого кандидата запиши node ID, путь, видимость, роль, структуру и
   отсутствие instance-связи. Отдели экранные/layout-контейнеры от собственно
   UI-блоков. Не освобождай блок от проверки только потому, что он имеет тип FRAME.
3. Найди ожидаемый компонент в применимой библиотеке: сначала по доступному
   mapping/правилу, затем по роли и выявленному семейству. Сравни структуру,
   вложенные элементы, варианты, размерные и layout-правила, доступные свойства
   и визуальное исполнение. Имя или одинаковый RGB/размер недостаточны. Поиск
   только по точному имени слоя также недостаточен: библиотечное имя может отличаться.
4. Зафиксируй результат сопоставления для каждого кандидата по категориям ниже.
   Несколько повторений одной причины можно объединить, перечислив все node IDs.
   Скрытые кандидаты учитывай отдельно от видимого интерфейса.

Наличие tokens, text styles, корректного Auto Layout и вложенной instance-иконки
не восстанавливает связь внешнего UI-блока с компонентом. После detach эти связи
могут сохраниться, поэтому они не снимают кандидат с проверки.

### Классификация и границы доказательства

| Результат | Когда использовать |
| --- | --- |
| Подтверждённый detach | Есть достоверные сведения об исходном компоненте и утрате instance-связи, в том числе прямое подтверждение дизайнера для конкретных узлов. Покажи источник подтверждения. |
| Подтверждённая ручная замена | Происхождение неизвестно, но mapping/правило требует конкретный компонент и вместо него обычные слои. История detach для этого вывода не нужна. |
| Подозрение на detach / ручную копию | Роль и сравнение с эталоном указывают на библиотечный UI-блок, но обязательность или происхождение не установлены. Покажи кандидата и эталон; не утверждай, что он точно был отсоединён. |
| Допустимая авторская композиция | Это экранный/layout-контейнер, уникальный блок или явно согласованное исключение. Укажи основание; отсутствие найденного эталона само по себе исключение не подтверждает. |
| Не проверено | Нужный эталон недоступен, поиск/сравнение не завершены или данных недостаточно. Укажи, что нужно для завершения. |

На скриншоте Layers различие иконок instance и frame подтверждает текущий тип
узла. Если дизайнер сообщает, что конкретные `limit` — отсоединённые компоненты,
зафиксируй это как его подтверждение и найди исходное семейство для рекомендации.
Без такого сообщения два `limit` типа FRAME — обязательные кандидаты на сравнение,
а не автоматически допустимые контейнеры и не автоматически подтверждённые detaches.
Этот пример иллюстрирует проверку; имена и правила конкретного продукта не становятся
обязательными для остальных библиотек.

### Условие завершения

Группа «Detaches и ручные замены» проверена только после обоих проходов, когда
для всех выделенных кандидатов есть результат сопоставления. Если остались
подозрения или непроверенные кандидаты, перечисли их и обозначь ограничение.
Не скрывай их формулировками «все instances связаны» или «подтверждённых detaches
нет». Без истории допускается вывод «подтверждённых случаев нет; кандидаты …
остаются неразрешёнными», но не общий вывод об отсутствии проблемы.

История detach не обязательна сама по себе: если все текущие связи и кандидаты
проверены и неразрешённых случаев нет, её отсутствие не делает ревью частичным.
Для нарушения покажи node, ожидаемый source component, основание ожидания и
следующий шаг. Замена на компонент — рекомендация, а не автоматическое действие.
Приоритет зависит от последствия, а не от самого факта отсутствия instance-связи.

## Переиспользование в реализации

Для исходных и рекомендуемых семейств проверь Code Connect, реализацию и stories
по [code-readiness.md](code-readiness.md). Отсутствие instance-связи и отсутствие
реализации — разные проблемы. У рекомендации заменить ручной блок укажи, есть ли
готовый компонент в коде и Storybook и покрывает ли он нужный сценарий. Не обещай
простую замену только по визуальному сходству или наличию Code Connect.

## Variables и styles

Определи, какие свойства должны быть связаны по реально применимым правилам:
цвета, типографика, эффекты, размеры/radii/spacing и другие токенизированные свойства.
Не требуй variables на каждом числовом значении. Авторская геометрия, изображения,
градиенты и значения без токена могут быть допустимы; это не освобождает от проверки
свойств, для которых правило или эталон действительно задаёт binding.

- Читай реальные variable bindings и style IDs, включая ranges смешанного текста,
  отдельные fills/strokes/effects и свойства вложенных узлов. MIXED не равно «без стиля».
  Свойство, оформленное через поддерживаемый published style, не обязано дублировать
  привязку прямой variable на узле. Проверь нужный style и его внутренние bindings,
  если от них зависит вывод.
- Выявляй локальные literals вместо требуемого token/style, переменные из неверной
  коллекции, несоответствующие роли tokens, потерянные bindings после override и
  неразрешимые ссылки. Совпадение RGB с токеном не доказывает правильную привязку;
  разные роли могут иметь одинаковый цвет в одной теме.
- Разрешай aliases до конечного значения в применимом mode. Не называй нормальный
  alias ошибкой, не заменяй его конечным literal. Проверяй тип и допустимость значения
  для свойства по доступным данным.
- Проверь наследуемый и явно переопределённый mode на экране и вложенных блоках.
  Нужны только заявленные темы/режимы: не требуй dark у light-only фичи. Если
  заявлены light/dark, проверь обе через доступное чтение resolved values и/или
  предоставленные варианты, не меняя исходник. Отсутствие второго mode в доступном
  чтении не доказывает отсутствия поддержки.
- Вынесенный в literal цвет может выглядеть правильно в light и сломаться в dark.
  Разделяй установленную потерю binding и ещё не проверенное визуальное последствие.

## Вывод и серьёзность

Покажи группы в отчёте по report.md. У каждого случая — node/свойство, фактическая
связь или literal, ожидаемый компонент/token/style и основание ожидания.
Не маскируй неизвестное общими словами «всё на компонентах» или «переменные есть».

Не назначай всем detaches одинаковый приоритет. Разрыв обязательного компонента
или систематическая потеря цветовых bindings может быть существенной проблемой;
блокер требует объяснения, почему это мешает согласованной передаче/сценарию.
Скрытый черновой фрагмент и допустимый уникальный блок не равны сломанному активному UI.
