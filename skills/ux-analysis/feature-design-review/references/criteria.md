# Критерии ревью готового макета

Выбирай направления по задаче и реальному сценарию. Этот список не обязывает
рисовать все возможные состояния, поддерживать все платформы или менять продукт.

| Направление | Что проверять при наличии такого поведения |
| --- | --- |
| Требования | Цель, аудитория, условия показа, обязательные данные и действия, ограничения этапа. Требование реализовано по смыслу, а не только упомянуто на экране. |
| Сценарий | Точка входа, следующий шаг, результат, возврат, отмена и сохранение введённого/выбранного. Основные ветки и значимые условия не противоречат друг другу. |
| Состояния | Начальное состояние, выбор, загрузка, успех, отсутствие данных, ошибка, ограничения доступа и недоступность действия — только применимые. Уже описанное компонентом или общим правилом не требует нового фрейма. |
| Сбои и восстановление | Что видит пользователь после ошибки, как повторяет действие, сохраняются ли данные, чем отличается отсутствие результатов от сбоя. Не придумывай технические сбои, не влияющие на дизайн. |
| Содержание | Понятность подписей и CTA, согласованность терминов, валют, единиц и условий; существенные ограничения видимы до действия, к которому относятся. Тестовые цифры не объявляются бизнес-правилом. |
| Визуальная иерархия | Основное действие различимо, смысловые группы читаются, акценты не конфликтуют с задачей. Конкретные перекрытия, нечитабельность, потеря контента и неоднозначные связи важнее вкусовых советов. |
| Компоненты и оформление | Проверка по library-usage.md: исходные и вложенные instances, detaches и ручные замены, принадлежность библиотеке, variables/styles, aliases и modes. Наличие правильного цвета на скриншоте не подтверждает binding. |
| Layout и контент | Длинные подписи, переменное число элементов, отсутствие изображения и ограниченная ширина — когда это реальные входы фичи. Прочитанные ограничения учитывай; без проверки не утверждай, что текст точно переполнится. |
| Адаптивность | Заявленные ширины/платформы, изменение компоновки, скролл, фиксированные элементы и safe area в соответствующем контексте. Один мобильный frame не доказывает поддержку всех ширин. Не требуй desktop для mobile-only задачи. |
| Доступность | Видимые проблемы чтения, информация только цветом, различимость действий, подписи полей, логика ошибок. Семантику, фокус, работу со скринридером и реальные hit areas оценивай лишь по доступным спецификациям/коду; статичный макет их не доказывает. |
| Движение и жесты | Существенные переходы, trigger/result, закрытие шторки, повторное действие, прерывание и reduced motion — если влияет на сценарий. Применимое прочитанное правило или стандартный библиотечный компонент может быть достаточен. Не требуй duration/easing для каждого перехода экрана. |
| Передача разработчику | Можно ли однозначно восстановить обязательный путь, контент, условия и применимый layout из всех доступных источников. Не требуй заданный шаблон документа, полный API компонента или техническую архитектуру от дизайнера. |

Разделяй три причины замечаний:

1. **Нарушение подтверждённого требования:** источник говорит X, макет показывает Y.
2. **Пробел решения:** без ответа нельзя однозначно реализовать применимый шаг;
   в прочитанных источниках ответа нет. Сформулируй пример ситуации и вопрос.
3. **Предложение:** возможное улучшение, не обязательное требование. Объясни
   ожидаемую пользу как гипотезу; не обещай рост конверсии или результат исследования.

Например, если задача требует показать итоговую стоимость до подтверждения, а она
появляется только на экране успеха, это расхождение. Если дизайнер предлагает
перенести уже видимую стоимость выше без подтверждённой проблемы, это предложение.
Если экран с итогом недоступен инструменту, соответствующее требование не проверено.

Не импортируй частные правила SP UI, AdTech, другой команды или публичного гайда
как требования этой фичи. Для точных нормативных утверждений нужны актуальный
первичный источник и подтверждённая применимость; иначе ограничься наблюдаемым
риском. Не объявляй соответствие WCAG по одному просмотру Figma.
