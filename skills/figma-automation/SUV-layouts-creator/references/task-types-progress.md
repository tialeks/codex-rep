# Три вида заданий и отображение прогресса

Эталон: [«Условия заданий»](https://www.figma.com/design/Yr8Cw6GqsShWUC94tqXTVY/?node-id=29534-112726), изучен 3 ноября 2026. Правила оплаты, состояния до открытия, иконок и двухслойной плашки — в [task-payment-methods.md](task-payment-methods.md).

## Типы и данные

Тип задания и способ оплаты — независимые параметры. Любой из трёх типов не означает автоматически карту Пэй: выбирать оплату из условий.

| Согласованное название вида | Цель | Прогресс в шторке | Что осталось в ячейке |
|---|---|---|---|
| Определённая сумма на количество транзакций | Заданное количество подходящих заказов/транзакций с указанной суммой | Сегментированная шкала и число выполненных / требуемых транзакций | Оставшееся число, сумма и способ оплаты, если указан |
| Любая сумма на количество транзакций | Заданное количество заказов/транзакций без требования к сумме | Такая же сегментированная шкала и счётчик транзакций | Оставшееся число покупок без выдуманной суммы |
| POS-оборот | Достичь заданной общей суммы покупок за любое число транзакций | Одна непрерывная шкала и накопленная сумма / целевая сумма | Оставшаяся сумма до цели |

Первый вид пользователь назвал **«Определённая сумма на количество транзакций»**, ранние поисковые формулировки не заменяют это название. POS-оборот — именно накопление общей суммы, а не минимальная сумма одной покупки и не требуемое число покупок. Не выводить из слова POS дополнительное ограничение «только офлайн»: такого условия пользователь не задавал.

Для первого вида сохранять сумму и её область действия из исходных условий. Если источник не поясняет, относится ли порог к каждой засчитываемой транзакции или к иному условию, уточнить это перед реальной сборкой; не превращать неоднозначный текст в POS-оборот по догадке.

## Точные формулировки примера

| Вид | Шторка | Счётчик | Нижняя плашка ячейки |
|---|---|---|---|
| Определённая сумма | «Совершите 3 заказа в Лавке на сумму от 1000 ₽» | 1/3 | «За ещё 2 заказа в Лавке от 1500 ₽ по карте Пэй» |
| Любая сумма | «Совершите 3 заказа в Лавке» | 1/3 | «За ещё 2 покупки в Лавке» |
| POS-оборот | «За заказы на общую сумму 1000 ₽» | 496/1000 | «За заказы ещё на 504 ₽ в Лавке» |

Это уже **начатое выполнение**, а не старт с нуля. Числа 3, 1, 1000, 1500, 496, 504 — демонстрационные данные.

В ячейках нет отдельной шкалы выполнения в основной части: прогресс выражен **остатком в нижней плашке**. Не добавлять шкалу в ячейку по аналогии со шторкой. По последнему уточнению пользователя **у получаемой категории задания подстрочника не будет**. Подстрочник «На покупку билетов» в демонстрационной ячейке Музыки — ранний пример, не переносить его в новые сборки заданий. Это уточнение относится к названию категории в ячейке; описание категории под заголовком шторки сохраняется по ранее изученному шаблону, если отдельно не отменено.

Слова «заказ», «покупка», «транзакция» выбирать по согласованным данным и редактуре; не объявлять одно слово универсальным для всех сервисов. В эталоне значимые части условия в нижней плашке выделены жирнее: сохранить смешанное форматирование при замене текста.

## Шкалы в шторках

Прогресс находится внутри **условия выполнения задания**, не в блоке метода оплаты:
- у вложенного center включено свойство progress;
- wrapper progress → Progress Group (View=default) → Element Slot;
- Progress Element: View=on-color, Size=m; проверенный component key `63c4e6913ffd5400e00e157950cfaaeb6fcb0a79`;
- высота полосы примера 6 px; рядом остаётся текстовый счётчик, занимающий собственное место.

Для количества транзакций в примере на цель 3 используется **три отдельных Progress Element**, один заполнен, два пусты; справа 1/3. Не изображать 1/3 одной непрерывной полосой и не оставлять три сегмента при другой целевой величине без проверки нужной конфигурации.

Для POS-оборота используется **один Progress Element** с заполненной и пустой частью. Текст 496/1000 означает накопление 496 из 1000; оставшаяся сумма 504. Никаких искусственных транзакционных сегментов.

Остаток считать из тех же данных, что счётчик: для количества max(0, цель − выполнено); для оборота max(0, целевая сумма − накоплено). Долю заполнения ограничивать диапазоном от 0 до 1. Проверять соответствие заливки числам; не копировать случайную долю из другого примера. Не придумывать правила учёта платежей, отмен, сроков или финального состояния: в этом обучении они ещё не разобраны.

## Расхождения демонстрационных данных

Не переносить в результат несогласованные данные из разных частей эталона:
- в первом виде ячейка показывает 1500 ₽, шторка — 1000 ₽;
- во втором виде ячейка показывает +7%, шторка — 8%;
- в POS-примере ячейка относится к Музыке с 10%, а шторка — к Маркету с 8%.

Эти примеры показывают **строение**, а не единый готовый оффер. В реальной категории название, ставка, брендовая шайба, порог и прогресс в ячейке и шторке должны происходить из одного подтверждённого набора условий. Не выводить из +7% универсальное правило о прибавке к уже действующей ставке без пояснения пользователя.


## Последнее уточнение: новые макеты в нулевом состоянии

После показа примеров пользователь выбрал для новых сборок **задание ещё не начато**. Начатые состояния из эталона нужны для понимания, не являются стартовыми данными макета.

- Для обоих видов на количество транзакций: выполнено 0, счётчик 0/N, все N сегментов пустые; в ячейке требуется полное количество N покупок/заказов.
- Для POS-оборота: накоплено 0, счётчик 0/целевая сумма, заполнение отсутствует; в ячейке остаток равен полной целевой сумме.
- Не подставлять 1/3, 496/1000 или остаток 504 ₽ из демонстрации.
- Не включать уточняющий подстрочник получаемой категории в ячейке задания, даже если он виден в старом примере. Не путать подстрочник с нижней плашкой: плашка с условием задания сохраняется.
- CTA по-прежнему ведёт в сервис выполнения задания.
- Если метод оплаты в нижней плашке слишком длинный, сохранять **усечение многоточием в одну строку** по эталону. Это особое правило этой плашки; не распространять его на подробный блок оплаты в шторке и не переписывать название метода ради сокращения.
- Начатый прогресс собирать только при отдельном запросе показать такое состояние или явно переданном состоянии для макета.

### Источники и геометрия прогресса

Progress Group / View=default — component key `fb06dcbf0c4612e1f5ae590e66d38799222d41a3`. В проверенном транзакционном примере Element Slot — HORIZONTAL, gap=4 px, ширина228; три Progress Element шириной около65.33 px используют FILL, блок счётчика — HUG. Счётчику оставлять место, не задавать всем сегментам ширину всей строки.

Цвет заполнения связан с переменной key `bdeede54163f4b1777f0be23f31a0dd2c6c13931`, пустой части — key `f590574fea28d7a2f34fc7ace7c134b6306e046d`. Сохранять библиотечные привязки, не заменять их подобранными вручную зелёным и серым.
