# Критическая проверка драфта СУВ — обязательная приёмка

Проводить после каждой сборки драфта и до сообщения о готовности. Применять и к дубликату готового макета, и к исправлению существующего. Наличие библиотечного инстанса, успешный ответ инструмента и правдоподобный скриншот не заменяют приёмку. Этот порядок имеет приоритет над историческими примерами.

## 1. Зафиксировать факты и применимые правила

Для каждого оффера сохранить источник (файл/вкладка/строка или подтверждение пользователя), смысловой ID, вид категории, источник выгоды, тип и размер выгоды, механизм оплаты, допустимые карты, канал и объект покупки, порог, оба лимита с периодами, отложку, исключения, наличие/текст/назначение кнопки, срок категории и требуемые состояния. Неприменимые поля отметить с причиной. Неизвестный обязательный факт не заменять догадкой.

Источник QR, допустимые карты и оформление оплаты — отдельные параметры. MP-QR сам по себе не доказывает оплату любой картой. Не переносить условия и оформление соседней категории только потому, что она выглядит похожей.

Затем пройти редактуру RU, EN при необходимости, выбрать конфигурацию компонентов и собрать драфт. Текст из инстанса считать непроверенным до сверки с источником и редактурой.

## 2. Прочитать структуру и измерить настройки

Для каждого применимого пункта зафиксировать: ожидаемое значение → фактическое → доказательство (node ID и прочитанное свойство либо проверенный рендер) → статус. Статусы: «подтверждено», «ошибка», «не проверено», «не применимо» с причиной. Не ставить подтверждение по памяти или без проверки текущего драфта.

| Область | Что проверить |
| --- | --- |
| Факты | Совпадение чисел, единиц, методов, каналов и исключений с источником; никакого наследования коммерческих условий из эталона. |
| Редактура | Каждый видимый текст проверен, порядок условий и регистр соблюдены; EN проверен отдельно по смыслу, глоссарию и длине. |
| MP-QR + любая карта | Только при подтверждении любой карты: зелёный фон Grass dark + light-tone/90 с bindings; после лимита/обоих лимитов последний фрагмент «за покупки на кассе по любой карте», со строчной «з». Не заменять его фразой про кнопку Пэй. |
| Инстансы | Дубликат настроенного эталона; связь с мастером и вложенные компоненты сохранены. Проверить слоты и overrides, а не только корневой mainComponent. |
| wrapper | Вертикальный, FILL/HUG, padding 0. Требуемая onboarding card внутри того же wrapper после List-item variants. Прочитать gap 10 и измерить реальное расстояние между видимыми блоками; внешний gap Content template 24 не подменяет этот промежуток. |
| Блок выгоды | Внутренний gap −20, padding Benefit block 16, высота по содержимому. Отсутствующие условия не оставляют пустых строк и разделителей. |
| Инструкция | Пэй — свёрнута и шеврон вниз; MP/CP-QR — развёрнута, правильные шаги и шеврон вверх; опции — по актуальной редактуре. Проверить реальную иконку, а не только Expanded. |
| Логотип Пэй | В инструкции кнопки Пэй — текст «Как платить через» + один библиотечный логотип в Center Slot. Не заменять логотип обычным текстом и не дублировать его при включении слота. |
| Ячейка | Сам List-item 288 px FIXED, нужный логотип, ставка и бейджи. Текстовый подстрочник только по правилам категории; не выводить туда порог/лимит автоматически. |
| Help | Если название помещается, text-before и label HUG, Help сразу после названия. Если не помещается — корректное усечение с сохранением Help. |
| Плашка задания | Внешние отступы по 16 для всех заданий; text-after слева 4, справа 0. Не распространять эти размеры на платёжную плашку обычной категории. |
| Высота и токены | Dynamic/HUG, пока содержимое помещается; Fullscreen только по переполнению. Радиусы 32 через Radius/3xl, корректные шрифты, цвета и прочие требуемые bindings. |
| Шайба | Правильный бренд, геометрия и толщина по эталону. Проверить фактический видимый силуэт и alpha-поля, положение, весь нижний/боковой контур. Размер слота 72×72 сам по себе ничего не доказывает. Для срока проверить отдельное согласованное уменьшение. |
| CTA и legal | Наличие по входным данным; дефолт подписи при пустом тексте. Не оставлять чужую ссылку из дубликата. Проверить доступный URL, срок и исключения, legal 11/12, только «Подробнее» link+underline, остальные диапазоны secondary. Не выдумывать отсутствующий адрес. |
| Состояния | У задания проверены до/после, награда и действие не смешаны; иконки, замок, плашки и CTA соответствуют состоянию. |

Найденная в библиотеке исходная иконка требует генерации шайбы по правилам, если нет подходящего готового ассета. Серый плейсхолдер допустим только после предусмотренного безуспешного поиска; обязательно отметить его в результате.

## 3. Посмотреть рендер и исправить

Открыть свежий рендер полного комплекта и рассмотреть содержимое в читаемом масштабе: видимые условия, переносы, обрезку, наложения, фон оплаты, знаки, шевроны, размер и центр шайбы. При необходимости увеличить конкретное проблемное место. Программное выделение не выдавать за реальные клики в интерфейсе.

При ошибке исправить затронутые слои, повторить связанные структурные/текстовые проверки и открыть новый рендер. Не считать прежний скриншот подтверждением после изменения макета. После проходящего рендера не повторять неизменившиеся проверки ради количества.

## 4. Критерий сдачи

**Запрещено объявлять комплект готовым, если применимая обязательная проверка не выполнена или известная ошибка не исправлена.** Драфт не равен принятому макету. При недоступном инструменте, источнике или нерешённом противоречии честно сообщить «проверка частичная»/«осталось», перечислив конкретные ограничения. Не утверждать, что проверены все условия, если проверен только текст или внешний вид.

В итоговом сообщении назвать результат, что реально проверено и что осталось. Не обещать абсолютную безошибочность: подтверждать готовность доказательствами текущей версии.
